# 웹사이트 제출 페이지 운영

`https://dmd2026.com/submit/`에서 팀 선택 → 기존 폴더·파일 확인 → 추가·교체·삭제 편집 → 파일 업로드 → 변경사항 반영 → GitHub PR 생성 → 자동 병합까지 처리합니다. 여러 번 나눠 반영해도 기존 파일은 유지합니다. 학생은 계정이나 팀 코드를 입력하지 않습니다. 병합 후 기존 Git 연동으로 Vercel이 배포합니다. 화면의 저장 완료는 병합 확인을 뜻하며 배포 성공을 보장하지 않습니다. 반영까지 몇 분 걸릴 수 있습니다.

## Vercel 배포 설정

이 저장소의 Vercel **Root Directory는 `cjdmd2026`**를 기준으로 작성했습니다. 현재 설정을 먼저 확인하세요. 저장소 루트와 사이트 루트는 서로 다릅니다.

- Framework Preset: **Other**
- Root Directory: **cjdmd2026**
- Install Command: `npm ci`
- Build Command: `npm run build`
- Output Directory: `public-dist`
- Node.js: **24.x** 권장 (22.15 이상 필요)
- 기존 정적 페이지와 에셋은 빌드 시 복사합니다. 서버 코드, 테스트, 환경변수 파일은 정적 출력에 포함하지 않습니다.
- `api/submission.js`는 Vercel Function입니다. `public-dist`만 수동 업로드하면 서버 함수는 배포되지 않습니다. Git 연결 또는 Vercel 프로젝트 배포를 사용하세요.

## 최초 연결

1. [R2 연결 가이드](./R2-SETUP.md)에 따라 비공개 Standard 버킷, CORS, 버킷 전용 Object Read & Write 키를 준비합니다. Vercel Hobby를 유지할 수 있습니다.
2. GitHub에서 `cjdmd2026/cjdmdwebsite` 하나만 대상으로 하는 인증 정보를 준비합니다. 현재 구현은 서버 전용 fine-grained PAT를 사용합니다. 최소 권한은 **Contents: Read and write**, **Pull requests: Read and write**, **Metadata: Read**입니다. 조직의 토큰 승인 정책이 있으면 승인까지 완료해야 합니다. GitHub Apps 사용을 원한다면 서버의 토큰 공급 부분을 설치 토큰 발급 방식으로 변경할 수 있습니다.
3. Vercel 환경변수를 설정합니다. 실제 비밀 값은 채팅·소스·이 문서에 넣지 않습니다.

| 변수 | 값 / 용도 |
|---|---|
| R2_ACCOUNT_ID | Cloudflare Account ID |
| R2_BUCKET_NAME | 전용 버킷 이름 (권장: dmd2026-submit) |
| R2_ACCESS_KEY_ID | 버킷 전용 Access Key ID |
| R2_SECRET_ACCESS_KEY | 버킷 전용 Secret Access Key |
| `SUBMISSION_GITHUB_TOKEN` | 위 저장소에만 권한을 부여한 GitHub 토큰 |
| `SUBMISSION_SIGNING_SECRET` | 임의의 충분히 긴 비밀 문자열, 최소 32자. 접수 확인권 서명용 |
| `SUBMISSION_GITHUB_REPOSITORY` | `cjdmd2026/cjdmdwebsite` |
| `SUBMISSION_BASE_BRANCH` | `main` (실제 운영 배포 브랜치와 일치시킬 것) |
| `SUBMISSION_SITE_PATH` | `cjdmd2026` (GitHub 저장소 안의 사이트 폴더) |
| `SUBMISSION_ORIGIN` | `https://dmd2026.com` |
| `SUBMISSIONS_ENABLED` | 연결·점검 완료 후 `true`, 접수 중지 시 `false` |

4. 환경변수 적용 후 **Redeploy**합니다. 설정이 없으면 페이지에 준비 중 안내가 나타나고 제출은 차단됩니다. 미설정 상태에서 성공한 것처럼 처리하지 않습니다.
5. 실제 공개해도 되는 파일로 점검합니다. 업로드만으로 PR이 생성되지 않는지 확인한 뒤 ‘변경사항 반영’을 누릅니다. PR 생성과 자동 병합, Vercel 배포를 확인합니다. **선택한 팀의 운영 사이트에 추가·교체·삭제가 적용되므로 임의의 테스트 변경을 반영하지 마세요.**

GitHub 토큰을 `VITE_`, `NEXT_PUBLIC_` 등 브라우저에 공개되는 환경변수에 넣으면 안 됩니다. 위 변수는 서버에서만 사용합니다. 자동 미리보기 배포가 연결돼 있다면 PR 자체에도 Vercel Preview가 생성될 수 있습니다.

운영 도메인의 리디렉션을 고려하여 `https://dmd2026.com`과 `https://www.dmd2026.com` 두 출처를 허용합니다. 다른 서브도메인은 자동으로 허용하지 않습니다.

기존 Blob의 미완료 접수는 자동 이전하지 않습니다. R2 접수 확인권을 별도로 저장하므로 새 페이지에서 같은 폴더를 다시 선택해 제출하세요. 이미 GitHub에 반영된 파일과 기존 Blob 원본은 이번 전환으로 삭제하지 않습니다.

## 자동 병합

- 별도 환경변수 없이 새 제출의 PR을 서버가 자동 병합합니다. 기존에 접수 완료된 PR은 소급 병합하지 않습니다.
- 현재 토큰의 **Contents: Read and write**, **Pull requests: Read and write** 권한을 사용합니다. GitHub의 `Allow auto-merge` 설정은 필요하지 않습니다. 서버가 REST 병합 API를 직접 호출합니다.
- 대상 저장소·기본 브랜치·접수 브랜치·커밋 SHA를 확인하고, 변경·삭제·이름 변경 파일 모두가 선택한 팀 폴더 안에 있는지 검사합니다. 검사한 SHA를 병합 요청에도 전달하며, 변경 파일 목록을 전부 확인할 수 없으면 중단합니다.
- 저장소에서 허용된 방식 중 squash → merge commit → rebase 순서로 선택합니다. 브랜치 보호·필수 승인·필수 검사를 해제하거나 우회하지 않습니다. 보호 규칙이나 충돌 때문에 병합할 수 없으면 PR을 보존하고 `접수 완료 · 자동 반영 확인 필요`로 안내합니다.
- 일시적인 GitHub 장애나 병합 가능 여부 계산 중에는 같은 PR을 재확인합니다. 병합 응답이 끊겨도 이미 병합된 PR을 확인해 완료 처리하며, 파일을 다시 올리거나 PR을 중복 생성하지 않습니다.
- 병합 성공 후 `submitted`와 `merged: true`를 기록합니다. 병합 단계의 최종 실패는 `merge_failed`이며, 접수 번호와 PR 번호를 보존하고 임시 저장공간을 정리합니다. 담당자는 보존된 PR에서 원인을 확인할 수 있습니다.

## 파일 관리 화면

- 팀 선택 시 현재 GitHub 기본 브랜치의 해당 팀 폴더를 불러옵니다. 폴더와 상단 경로를 눌러 이동할 수 있습니다.
- ‘파일 추가’는 현재 폴더에, ‘폴더 추가’는 선택한 폴더 이름과 내부 구조를 유지해 현재 위치에 추가합니다. ‘사이트 폴더 가져오기’는 선택한 최상위 폴더 이름을 제거하고 팀의 루트에 파일을 추가합니다.
- ‘새 폴더’로 위치를 만든 뒤 그 안에 파일을 넣을 수 있습니다. Git에 빈 폴더 자체는 저장하지 않습니다.
- 파일·폴더의 ‘삭제’ → ‘삭제 예정에 추가’는 화면상의 변경 계획입니다. ‘삭제 취소’로 되돌릴 수 있습니다. 최종 확인 체크와 ‘변경사항 반영’을 눌러야 실제 삭제됩니다. 파일 없이 삭제만 반영할 수도 있습니다.
- 처음 반영할 때는 비어 있지 않은 루트 `index.html`이 필요합니다. 이후 부분 업로드에는 다시 포함하지 않아도 됩니다. 유일한 `index.html`을 삭제한 상태로는 반영할 수 없습니다.
- 이번 업로드와 기존 파일을 합친 최종 상태를 브라우저와 서버에서 검사합니다. 최대 **2,000개 / 500 MiB**, 개별 업로드 파일은 95 MiB입니다. 한 번에 추가·교체·삭제할 경로도 합계 2,000개까지입니다.
- 기존 팀 폴더의 트리 SHA를 접수에 기록합니다. 업로드 준비·GitHub 저장·자동 병합 전에 팀 폴더가 바뀌었는지 검사해 다른 제출의 파일을 덮어쓰지 않습니다. 다른 팀 폴더만 바뀌었다면 계속 진행할 수 있습니다.
- 업로드 시작 후에는 해당 접수의 추가·교체·삭제 목록을 고정합니다. 수정하려면 ‘업로드 취소 · 다시 편집’을 사용합니다. 반영 후 ‘이 팀 파일 계속 편집’으로 최신 목록을 불러와 다음 변경을 준비합니다. 임시 저장공간 정리가 끝난 뒤 다음 접수를 시작합니다.

## 업로드와 재시도

- **동시에 한 접수만 허용**합니다. 팀·폴더 선택은 누구나 가능하지만 업로드 시작부터 파일 검증·GitHub 저장·임시 파일 정리까지 서버의 단일 접수 슬롯을 점유합니다. 같은 팀의 다른 브라우저도 별도 접수이므로 대기합니다. 다른 팀에는 제출 중인 팀 이름과 대기 안내가 표시되며 화면이 보이는 동안 1분마다 다시 확인합니다.
- 슬롯은 비공개 R2의 `submission-control/active.json`에 저장합니다. 최초 생성은 덮어쓰기 금지, 갱신은 ETag 조건부 쓰기를 사용하므로 여러 Vercel 함수가 동시에 접수를 시도해도 하나만 허용합니다. 업로드 토큰 발급·파일 확인·최종 제출·GitHub 처리 단계에서 접수 소유권을 다시 검사합니다.
- 진행 중에는 접수 기한을 갱신합니다. **마지막 활동 후 약 30~35분**이 지나면 다음 상태 확인 또는 접수 요청에서 중단된 접수의 임시 파일과 검증 기록을 정리합니다. 유휴 상태로 창만 열어두면 기한이 연장되지 않습니다. 별도 Cron 설정은 필요 없으며, 요청이 전혀 없으면 정리는 다음 요청 때 실행됩니다.
- 성공·실패·취소 뒤에도 이미 발급된 업로드 토큰으로 파일이 뒤늦게 도착할 수 있습니다. 토큰 만료와 안전 대기 시간까지 **최대 약 12분** 슬롯을 유지한 뒤 파일을 정리하고 다음 접수를 받습니다. 정리에 실패하면 슬롯을 열지 않고 재시도합니다. 기존 접수 기록의 성공 상태와 PR 번호는 보존합니다.
- 새 접수 시 저장소 사용량과 제출할 파일 크기를 함께 확인해 900 MiB를 넘으면 시작을 거절합니다. 이는 무료 제공량을 고려한 운영 제한이며 R2 자체의 최대 용량은 아닙니다. 다른 용도로 올린 파일이나 이전 버전의 남은 업로드는 자동 삭제하지 않습니다. 동시 접수 제한은 월별 전송량·작업 횟수 한도를 늘리지 않습니다.
- PC의 폴더 선택 기능(`webkitdirectory`)으로 폴더 구조를 보존합니다. ZIP을 만들 필요가 없습니다. React·Vite는 빌드된 `dist` 폴더를 ‘사이트 폴더 가져오기’로 선택합니다.
- 운영 제한: **기존 파일 포함 전체 500 MiB, 업로드 파일당 95 MiB, 최대 2,000개 파일**. 기존 ZIP 200 MiB 제한은 폴더 제출에 적용되지 않습니다. 큰 영상은 압축하거나 외부 주소로 연결해야 합니다.
- 제출 전 이미지는 디자인 도구의 ‘웹용으로 저장’ 또는 ‘내보내기’로 저장하고, 화면에 필요한 해상도와 품질로 조절해 용량을 최소화합니다. PNG는 가급적 피하고 꼭 필요한 경우에만 사용합니다. 저장 후 이미지와 글자의 선명도를 확인합니다. 이 안내는 제출 페이지의 기본 안내와 ‘파일 준비 방법 자세히 보기’에 표시됩니다.
- 브라우저에서 경로·크기·SHA-256 목록을 만든 뒤 서버가 경로와 한도를 다시 검증해 고정된 접수 기록을 생성합니다. 상위 경로 탈출, 숨김·설정 파일, 개발 의존성, 실행 파일, 중복 이름, 파일/폴더 충돌을 차단합니다. macOS 부가 파일은 선택 목록에서 제외합니다.
- 각 파일은 비공개 R2의 접수별 고정 경로에 직접 전송합니다. 파일당 최대 95 MiB의 단일 PUT으로 전송합니다. 파일 본문은 Vercel Function 요청 본문을 거치지 않습니다. 덮어쓰기를 허용하지 않으며 서명 URL은 등록된 파일의 경로·정확한 크기·덮어쓰기 금지 조건으로 제한합니다.
- 서버는 전송된 실제 크기와 SHA-256을 확인한 후 파일별 완료 기록을 저장합니다. 손상된 파일은 해당 파일만 삭제해 재전송할 수 있습니다. 전송 응답을 잃었더라도 확인 요청으로 이미 완료된 파일을 찾습니다.
- **업로드 시작 / 일시정지 / 남은 파일 이어 올리기 / 실패한 파일 재시도**를 지원합니다. 파일 목록에서 각 파일의 진행 상태와 오류를 볼 수 있습니다. 일시정지 중이던 파일 자체는 다시 전송할 수 있지만 완료된 파일은 건너뜁니다.
- 한 접수 안에서 최대 **4개 파일을 동시에 업로드·검증**합니다. 다른 팀은 기존처럼 대기합니다. 새 접수의 첫 전송은 존재 여부 조회를 생략하고, 재시도·새로고침으로 복구한 파일은 서버에 이미 저장되었는지 먼저 확인합니다. 업로드 후 크기·내용 검증은 모두 유지합니다.
- 일시정지나 서버 오류 시 대기 파일을 시작하지 않고 진행 중인 업로드·확인 요청을 모두 중단합니다. 중단된 요청이 정리될 때까지 편집과 최종 제출을 잠그고, 재시도 시 저장 여부를 다시 확인합니다. 전체 진행률은 동시에 전송 중인 파일의 바이트를 합산합니다. 이 개선은 실제 회선·서버 응답에 따라 효과가 달라지며, GitHub 저장·배포 시간이나 R2 작업 횟수 제한을 없애지는 않습니다.
- 접수 확인권은 브라우저 `localStorage`에 저장되며 24시간 유효합니다. 단, **업로드 이어 올리기는 마지막 활동 후 30분 이내**에만 가능합니다. 같은 브라우저에서 같은 폴더를 다시 선택하면 검증 완료된 파일은 재전송하지 않습니다. 파일 내용·이름·개수가 바뀌면 `업로드 취소 · 새 제출 시작`으로 이전 접수를 닫고 새로 시작해야 합니다. 시크릿 모드 종료나 브라우저 데이터 삭제 후에는 이어 올릴 수 없습니다.
- **업로드만으로 PR을 생성하지 않습니다.** 모든 파일의 서버 검증 완료 기록이 있어야 사용자의 `제출 완료` 요청을 수락합니다. 브라우저를 조작해도 미완성 폴더를 최종 제출할 수 없습니다. 업로드 콜백은 최종 제출을 시작하지 않습니다.
- 최종 제출 후에는 새 파일만 GitHub에 하나씩 전달해 메모리에 전체 폴더를 적재하지 않습니다. 기존 파일의 Git blob SHA를 유지하고, 요청한 변경만 담은 PR 하나를 자동 병합한 뒤 배포를 시작합니다. 최종 트리가 기존과 같으면 PR 없이 ‘변경 없음’으로 완료합니다.
- 서버 처리 자동 재개는 페이지가 열린 동안 진행됩니다. 창을 닫아도 진행 중인 호출은 계속되지만 시간제한·일시 오류 후에는 페이지를 다시 열어 상태를 확인해야 합니다. 영구 작업 큐는 포함하지 않았습니다.
- Vercel BotID Basic, 정확한 Origin 검사, IP별 시간당 100회 신규 접수 제한을 유지합니다. 팀 선택은 소속 인증이 아닙니다.
- PR 성공·실패·취소 또는 접수 만료 후 슬롯을 해제하기 전에 해당 접수의 원본 파일과 검증 기록을 삭제합니다. 소량의 접수 기록과 IP별 접수 제한 기록은 남으므로 접수 기간 종료 후 관리자가 정리할 수 있습니다.
- R2는 무료 제공량 초과 시 사용량 과금됩니다. Vercel Functions에는 별도로 플랜의 사용량 제한이 적용됩니다. 공개 접수 전에 사용량 한도와 알림을 확인하세요.

## 로컬 확인

```sh
npm ci
npm test
npm run build
npm run dev
```

`http://127.0.0.1:4173/submit/`에서 확인합니다. 기본 로컬 실행은 실제 토큰 없이 준비 중 화면을 제공합니다. 실제 R2 CORS·키와 GitHub 권한은 Vercel에서 연결 후 별도 확인이 필요합니다. 테스트는 실제 GitHub에 PR을 생성하지 않습니다.
